# NovelScope API V0.2.0 番茄小说接入设计

## 1. 背景

NovelScope API V0.1 只支持起点中文网，并保存四类 Top 10 榜单的历史快照以及每本书最近一次成功详情。V0.2.0 增加番茄小说，同时保留现有业务边界：采集层负责访问和解析站点，业务 Service 负责完整性、错误语义、TTL 与 stale 回退，Repository 仍是 Prisma 的唯一业务访问边界。

番茄榜单 URL 为：

```text
https://fanqienovel.com/rank/{channel}_{type}_{categoryId}
```

其中：

- `channel=0` 表示女频，`channel=1` 表示男频；
- `type=1` 表示新书榜，`type=2` 表示阅读榜；
- `categoryId` 必须来自对应频道的有限分类白名单；
- 男频和女频的分类 ID 不重复。

例如 `0_1_1139` 表示女频、古风世情分类的新书榜。

## 2. 目标

V0.2.0 需要完成以下能力：

1. 新增平台 `fanqie`，并保持起点与番茄爬虫相互隔离。
2. 继续使用统一榜单和详情 API。
3. 使用番茄原始参数组合 `0_1_1139` 作为机器查询键 `rankTypeKey`。
4. 使用 `女频-新书榜-古风世情` 作为人类可读的 `rankType`。
5. 保存番茄 Top 10 榜单历史快照，并支持番茄书籍详情的 TTL、强制刷新和 stale 回退。
6. 起点每日 06:00 刷新，番茄在官方午夜更新后于每日 00:30 刷新，时区均为 `Asia/Shanghai`。
7. 为后续站点提供可复用的“平台榜单目录 + 独立站点模块”扩展方式。

## 3. 非目标

V0.2.0 不包括：

- 榜单历史查询接口；
- 分类发现或自动同步机制；
- 任意 `categoryId` 的动态采集；
- 多站点数据合并、同书识别或跨平台去重；
- Swagger、鉴权或自定义全局错误包装；
- 在自动化测试中访问真实外部站点。

番茄分类 ID 与分类名称的一一对应表由项目方提供并作为静态平台配置。配置项缺少频道、分类 ID 或分类名称时不得启用，也不得进入定时任务。

## 4. 第三方库评估

项目已经依赖 Axios、Cheerio 和 Playwright，不需要新增采集依赖。

- Axios 适合普通 HTTP 请求，但无法稳定复现番茄页面初始化、浏览器 Cookie 和同源请求环境，因此不作为番茄主采集方式。
- Playwright 能读取页面中的 `window.__INITIAL_STATE__`，也能在已打开的番茄页面内执行同源 `GET /page/{bookId}`，作为主采集引擎。
- Cheerio 用于从详情 HTML 中定位内嵌 JSON；数据只通过 `JSON.parse` 或页面中已经生成的可序列化对象读取，不执行从 HTML 提取出的脚本文本。

## 5. 总体架构

```text
AppModule
├── RankingsModule ──> CrawlersModule + DatabaseModule
├── BooksModule ─────> CrawlersModule + DatabaseModule
└── CrawlersModule
    ├── QidianModule
    │   ├── QidianRankingCatalog
    │   ├── QidianRankingCrawler
    │   └── QidianBookCrawler
    └── FanqieModule
        ├── FanqieRankingCatalog
        ├── FanqieBrowserClient
        ├── FanqieRankingParser / Crawler
        └── FanqieBookParser / Crawler
```

`QidianModule` 和 `FanqieModule` 互不依赖。`CrawlersService` 仅按平台返回对应的榜单目录、榜单爬虫和详情爬虫。业务模块不直接依赖站点实现。

## 6. 平台与榜单目录

### 6.1 通用定义

榜单目录对业务层提供稳定定义：

```ts
interface RankingDefinition {
  platform: Platform;
  rankTypeKey: string;
  rankType: string;
}

interface RankingCatalog {
  list(): readonly RankingDefinition[];
  resolve(rankTypeKey: string): RankingDefinition | null;
}

interface RankingCrawler {
  crawl(rankTypeKey: string): Promise<CrawledRanking>;
}
```

`rankTypeKey` 是平台内部机器标识和数据库查询键；`rankType` 是快照中保存并向 API 使用者展示的名称。业务层不解析站点参数，仅通过所选平台的目录校验键是否可用。

采集结果增加机器键：

```ts
interface CrawledRanking {
  platform: Platform;
  rankTypeKey: string;
  rankType: string;
  sourceUrl: string;
  fetchedAt: Date;
  items: CrawledRankingItem[];
}
```

### 6.2 起点目录

起点保留现有四个机器键，同时将展示名称规范化：

| `rankTypeKey` | `rankType` |
| --- | --- |
| `yuepiao` | `月票榜` |
| `hotsales` | `畅销榜` |
| `recom` | `推荐榜` |
| `collect` | `收藏榜` |

起点爬虫只能解析这四个键。

### 6.3 番茄目录

番茄配置分别维护频道、榜单类型和频道分类：

```ts
const FANQIE_CHANNELS = {
  "0": "女频",
  "1": "男频",
} as const;

const FANQIE_RANKING_TYPES = {
  "1": "新书榜",
  "2": "阅读榜",
} as const;

const FANQIE_CATEGORIES_BY_CHANNEL = {
  "0": [{ id: "1139", name: "古风世情" }],
  "1": [],
} as const;
```

上例只用于说明已知映射和配置结构；发布 V0.2.0 时使用项目方提供的完整正式分类表替换数组内容。未知名称的分类 ID 不生成榜单定义。

每个频道分类与两种榜单类型组合，生成：

```text
rankTypeKey = {channel}_{type}_{categoryId}
rankType    = {频道名称}-{榜单类型名称}-{分类名称}
```

示例：

```text
0_1_1139 -> 女频-新书榜-古风世情
0_2_1139 -> 女频-阅读榜-古风世情
```

目录初始化时必须关闭式校验：

- 频道只能是 `0` 或 `1`；
- 类型只能是 `1` 或 `2`；
- 分类 ID 必须是非空纯数字字符串；
- 分类名称必须是去除首尾空白后的非空字符串；
- 同一频道内不得出现重复分类 ID 或名称；
- 两个频道之间不得出现相同分类 ID 或分类名称；
- 生成的 `rankTypeKey` 和 `rankType` 都必须唯一。

配置不合法时应用启动失败，不带着不完整目录运行。

## 7. API 设计

现有路由结构保持不变，路径中的最后一段语义改为 `rankTypeKey`：

```text
GET  /v1/rankings/:platform/:rankTypeKey
POST /v1/rankings/:platform/:rankTypeKey/refresh
POST /v1/rankings/:platform/refresh

GET  /v1/books/:platform/:bookId
POST /v1/books/:platform/:bookId/refresh
```

番茄示例：

```text
GET  /v1/rankings/fanqie/0_1_1139
POST /v1/rankings/fanqie/0_1_1139/refresh
GET  /v1/books/fanqie/1234567890
```

榜单快照响应同时返回机器键和展示名称。下面只展示顶层识别字段：

```json
{
  "platform": "fanqie",
  "rankTypeKey": "0_1_1139",
  "rankType": "女频-新书榜-古风世情",
  "sourceUrl": "https://fanqienovel.com/rank/0_1_1139",
  "fetchedAt": "2026-07-23T16:30:00.000Z"
}
```

`refreshAll` 的每个结果项也返回 `rankTypeKey` 和 `rankType`，使失败项无需解析 URL 即可定位。

请求校验顺序如下：

1. 校验 `platform` 属于支持列表；
2. 从该平台的 `RankingCatalog` 直接解析 `rankTypeKey`；
3. 目录中不存在的键返回 `400`；
4. 合法查询直接使用 `platform + rankTypeKey` 访问 Repository，不通过 `rankType` 反向查询。

起点的路由机器键保持不变，但响应会新增 `rankTypeKey`，并将原来 `rankType=yuepiao` 等值改为 `月票榜` 等中文展示名称。这是 V0.2.0 已确认的响应语义调整，现有调用方需要改为使用 `rankTypeKey` 做程序判断，不再依赖 `rankType`。

## 8. 数据库模型与迁移

`RankingSnapshot` 新增非空 `rankTypeKey`：

```prisma
model RankingSnapshot {
  id          String        @id @default(uuid()) @db.Uuid
  platform    String
  rankTypeKey String
  rankType    String
  sourceUrl   String
  fetchedAt   DateTime      @db.Timestamptz(3)
  createdAt   DateTime      @default(now()) @db.Timestamptz(3)
  items       RankingItem[]

  @@index([platform, rankTypeKey, fetchedAt(sort: Desc)])
}
```

迁移必须保留全部历史快照：

1. 新增可空 `rankTypeKey`；
2. 将现有起点行的旧 `rankType` 值回填到 `rankTypeKey`；
3. 将现有起点 `rankType` 转换为 `月票榜`、`畅销榜`、`推荐榜`、`收藏榜`；
4. 验证所有行均已回填；
5. 将 `rankTypeKey` 改为非空；
6. 删除旧 `(platform, rankType, fetchedAt)` 索引并建立 `(platform, rankTypeKey, fetchedAt DESC)` 索引。

迁移不得删除或重新创建历史快照、榜单项或书籍关系。`Book` 的 `(platform, externalBookId)` 唯一约束已经满足多平台隔离要求，无需修改。

Repository 的最新榜单查询签名改为：

```ts
findLatest(platform: Platform, rankTypeKey: string): Promise<RankingSnapshot | null>
```

保存时同时写入 `rankTypeKey` 和 `rankType`。

## 9. 番茄榜单采集

### 9.1 浏览器流程

`FanqieBrowserClient` 复用一个 Playwright 浏览器实例，每次请求创建隔离上下文：

1. 根据目录中已解析的 `rankTypeKey` 构造 `/rank/{rankTypeKey}`；
2. 只允许 `https://fanqienovel.com`，拒绝凭据、协议相对地址和其他域名；
3. 使用 Playwright 打开榜单页面；
4. 校验最终 URL 的 origin 和 pathname 与请求榜单一致；
5. 等待 `window.__INITIAL_STATE__` 出现；
6. 在页面上下文中只选择并返回榜单解析需要的可序列化数据；
7. 关闭本次浏览器上下文。

浏览器实例在 Nest 模块销毁时关闭。HTTP 401、403、429、登录页、验证码页、缺少初始状态、超时和非可信重定向都转换为站点内部错误，不向 API 暴露上游细节。

### 9.2 解析与完整性

番茄榜单解析器是无 I/O 的纯逻辑。它从初始状态中的榜单列表读取数据，规范化后截取前 10 项，并返回 `CrawledRanking`。

业务 Service 继续执行最终完整性门禁：

- `platform`、`rankTypeKey` 和 `rankType` 必须与请求定义一致；
- `sourceUrl` 必须非空；
- 必须恰好有 10 项；
- 排名必须为 1 至 10 的唯一整数；
- 书籍 ID 必须唯一；
- 书籍 ID、标题、作者和来源 URL 必须完整。

任何校验失败都不保存快照。

### 9.3 榜单字段映射

核心字段映射：

| 番茄字段 | NovelScope 字段 |
| --- | --- |
| `bookId` | `externalBookId` |
| `bookName` 或榜单标题字段 | `title` |
| `authorName` 或 `author` | `author` |
| 封面字段 | `coverUrl` |
| `/page/{bookId}` | `sourceUrl` |

可选榜单数据写入规范化后的 `metrics`：

```json
{
  "readCount": 123456,
  "wordCount": 800000,
  "creationStatus": "连载中",
  "lastChapterTitle": "最新章节",
  "category": "古风世情"
}
```

不存在的可选字段不写入 `metrics`。数值使用现有纯函数规范化，拒绝非有限值和超出安全范围的整数。

## 10. 番茄详情采集

详情爬虫只接受纯数字 `bookId`：

1. 创建隔离浏览器上下文并打开 `https://fanqienovel.com/`，建立可信的番茄同源页面环境；
2. 在页面环境中使用同源 `fetch('/page/{bookId}', { credentials: 'include' })`；
3. 返回响应状态、响应 URL 和 HTML；
4. 校验响应为成功状态，origin 为 `https://fanqienovel.com`，pathname 与请求书籍 ID 一致；
5. 限制响应内容大小并检测访问受限页面；
6. 使用纯解析器从内嵌 JSON 中读取详情。

详情字段映射：

| 番茄字段 | NovelScope 字段 |
| --- | --- |
| `bookName` | `title` |
| `authorName` 或 `author` | `author` |
| `abstract` | `description` |
| 封面字段 | `coverUrl` |
| `categoryV2` 与标签 | 去重后的 `genres` |
| 状态字段 | `bookStatus` |
| 字数字段 | `wordCount` |
| 其他有价值且可 JSON 序列化的字段 | `metadata` |

解析器必须验证页面中的书籍 ID 与请求一致。缺少标题、作者或来源 URL 时拒绝结果。可选字段缺失时返回 `null`、空数组或省略对应 metadata 项，不伪造值。

## 11. 业务错误语义

- 不支持的平台或未登记的 `rankTypeKey` 返回 `400`。
- 合法榜单键没有历史快照时返回 `404`。
- 单榜采集、解析、完整性校验或持久化失败时返回安全的 `502`。
- `refreshAll` 动态遍历平台目录；单项失败记录 `RANKING_REFRESH_FAILED`，不停止后续榜单。
- 榜单失败不写入部分数据，也不修改旧快照。
- 详情缓存未过期时直接返回数据库结果。
- 详情过期且自动刷新失败时返回最近一次成功详情并标记 `stale: true`。
- 强制详情刷新失败时返回 `502`，不覆盖最近一次成功详情。

内部日志记录平台、`rankTypeKey`、错误消息和堆栈；HTTP 响应不包含上游 HTML、URL 凭据、浏览器错误详情或内部路径。

## 12. 定时任务与配置

现有全局启用开关继续控制榜单定时采集。Scheduler 注册两个独立任务：

| 平台 | 任务名 | 默认 Cron | 时区 |
| --- | --- | --- | --- |
| 起点 | `rankings-refresh:qidian` | `0 0 6 * * *` | `Asia/Shanghai` |
| 番茄 | `rankings-refresh:fanqie` | `0 30 0 * * *` | `Asia/Shanghai` |

为保持现有部署兼容性，当前 `RANKING_REFRESH_CRON` 继续控制起点任务；新增 `FANQIE_RANKING_REFRESH_CRON` 控制番茄任务。两者共用现有 `RANKING_REFRESH_TIME_ZONE`，默认 `Asia/Shanghai`。

番茄任务按目录稳定顺序串行刷新全部定义。每个 CronJob 使用 `waitForCompletion: true` 防止自身重入。关闭应用时停止并删除两个任务，等待正在执行的回调结束，然后由各站点模块关闭浏览器资源。

新增 `FANQIE_REQUEST_TIMEOUT_MS`，采用与现有起点请求超时相同的校验规则和默认值。配置为空、非正整数或超过允许上限时应用启动失败。

## 13. 测试策略

### 13.1 单元测试

新增或扩展以下测试：

- 平台类型接受 `qidian` 和 `fanqie`；
- 起点目录只接受四个起点键；
- 番茄目录生成确定顺序的全部组合；
- 番茄目录拒绝非法频道、非法类型、重复分类、跨频道重复 ID、空名称和重复生成键；
- `CrawlersService` 将请求路由到正确站点，拒绝跨站点榜单键；
- 番茄榜单解析器覆盖正常数据、可选字段缺失、重复书籍、条目不足、必填字段缺失、错误初始状态和无效数值；
- 番茄详情解析器覆盖 `author`/`authorName`、简介、分类、标签、状态、字数、可选字段缺失和错误书籍 ID；
- 番茄浏览器客户端拒绝跨域 URL、错误重定向、访问受限状态和非数字书籍 ID；
- Service 按 `platform + rankTypeKey` 查询，并同时校验爬虫返回的机器键和展示名称；
- Scheduler 注册两个正确的 CronJob，并在销毁时等待和清理资源。

Fixture 放在 `test/fixtures/fanqie/`。解析器测试只使用固定 HTML 或序列化初始状态，不访问网络。

### 13.2 数据库与 HTTP E2E

真实 PostgreSQL E2E 继续通过现有数据库身份门禁运行，并覆盖：

- `RankingSnapshot.rankTypeKey` 的保存和最新快照查询；
- 起点与番茄相同外部书籍 ID 的平台隔离；
- 番茄榜单快照的事务完整性和不可变历史；
- 番茄详情 upsert、TTL、stale 回退和强制刷新；
- `400`、`404`、`502` 及 `refreshAll` 部分失败响应；
- 应用和 Prisma 连接正常关闭。

E2E 必须使用真实 AppModule、Controller、Service、Repository 和 Prisma，只覆盖外部爬虫边界。未预期的真实网络访问立即失败。

## 15. 完成标准

V0.2.0 在满足以下条件后视为完成：

1. 完整正式番茄分类映射已写入平台目录，并通过启动校验。
2. 起点现有四类榜单和详情行为没有回归。
3. 番茄所有已配置榜单可按 `rankTypeKey` 查询、刷新并保存 Top 10 历史快照。
4. 番茄详情可以缓存、强制刷新并在自动刷新失败时 stale 回退。
5. 起点和番茄定时任务分别按 06:00 和 00:30 运行。
6. 数据库迁移保留历史数据并完成起点 `rankTypeKey` 回填及中文名称转换。
7. 单元测试、Lint、构建、TypeScript 检查和安全数据库 E2E 全部通过。
8. API 与环境文档已更新，版本号为 `0.2.0`。
9. 至少一个番茄榜单和一本番茄书籍完成受控人工冒烟采集，并记录采集时间与结果。
